# SDD 主工作流：规格驱动开发

一个功能从想法到交付，按以下五个阶段顺序推进。**每个阶段结束必须过对应的质量门禁**（见 `harness/quality-gates/gates.md`），门禁不过不得进入下一阶段。

```
① 规格 Specify ──▶ ② 计划 Plan ──▶ ③ 任务 Tasks ──▶ ④ 实现 Implement ──▶ ⑤ 交付 Deliver
   [G1 规格门禁]      [G2 计划门禁]     [G3 任务门禁]      [G4 实现门禁]        [G5 交付门禁]
```

## ① 规格 Specify

- 在 `specs/` 下新建目录：`NNN-feature-name/`（NNN 为递增序号），从 `specs/TEMPLATE.md` 复制模板写 `spec.md`。
- 规格只写：用户场景、功能需求（可编号的 FR-x）、验收标准（可验证的 AC-x）、明确的非目标（Out of Scope）。
- 与用户确认规格，状态置为「已确认」。**歧义必须在此阶段消除，不留到实现阶段猜。**

## ② 计划 Plan

- 在规格目录下写 `plan.md`：技术方案、涉及的文件/模块、依赖变更、风险与权衡。
- 方案必须符合宪法（最小改动、不引入规格外依赖），并与 `harness/context/domain.md` 中的现有架构一致。

## ③ 任务 Tasks

- 在规格目录下写 `tasks.md`：把计划拆成可独立验证的小任务，每个任务标注对应的 FR-x 和验收方式。
- 任务粒度：一个任务一次能做完、能单独验证。

## ④ 实现 Implement

- 按任务逐个实现，每完成一个任务立即运行其验收方式。
- 代码风格跟随所在模块现有约定；新增测试跟随项目现有测试约定。
- 每完成一个任务在 `tasks.md` 中勾选，全部完成后过 G4 实现门禁。

## ⑤ 交付 Deliver

- 过 G5 交付门禁：全量检查 + 端到端验证 + 规格回溯（每条 AC-x 都有验证证据）。
- 更新规格状态为「已实现」；如实现中与规格有偏差，先更新规格再走门禁。
- 同步更新受影响的 `harness/context/` 文档与根 README。

## 变更流程（规格已确认后要改）

1. 修改 `spec.md`，在「变更记录」中追加一条：日期、改了什么、为什么。
2. 若已写 `plan.md` / `tasks.md`，同步修订。
3. 重新过受影响的门禁。
