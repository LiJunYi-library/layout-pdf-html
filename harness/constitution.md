# 宪法（Constitution）

本文件是项目的最高准则。任何规格、计划、代码、评审与它冲突时，以本文件为准。
修改宪法本身需要明确的用户指令，并在文件中记录修改原因。

## 第一条：规格先行（Spec-Driven Development）

- 任何功能、任何行为变更，必须先在 `specs/` 下存在对应规格，且规格状态为「已确认」后才允许写实现代码。
- 规格是唯一的真相来源。代码与规格不一致时，要么改代码，要么走变更流程改规格——不允许两者 silently 漂移。
- 规格用用户的语言写「做什么、为什么、怎么算对」，不写实现细节。

## 第二条：门禁必过（Quality Gates）

- 每个开发阶段（规格 → 计划 → 实现 → 交付）结束，必须通过 `harness/quality-gates/gates.md` 中对应的门禁。
- 门禁失败 = 停止前进，修复后重过。禁止注释掉检查、降低阈值、跳过测试来「让门禁变绿」。
- 验证必须基于真实运行结果：构建输出、测试报告、接口响应、生成文件的实际内容。

## 第三条：最小改动（Minimal Change）

- 只做规格要求的事。不顺手重构、不美化无关代码、不引入规格之外的依赖和配置。
- 每一处改动都能追溯到规格的某一条要求；追溯不到的改动不进库。

## 第四条：诚实交付（Honest Delivery）

- 没跑过的代码不说「完成」；跑过但失败的不说「通过」；部分完成就明确说完成了哪部分。
- 遇到阻塞（缺凭据、缺信息、矛盾需求）如实上报，不猜测着硬做。
- 证据优先：用命令输出、文件内容、截图说话，不用措辞粉饰。

## 第五条：人机同规（One Rulebook）

- 本治理层对人类开发者和 AI agent 一视同仁。人不享有跳过规格的特权，AI 不承担心照不宣的义务。
- 所有规则必须写成明文放在 `harness/` 里；口头的、隐式的规则不存在。
