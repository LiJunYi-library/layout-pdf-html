# 质量门禁（Quality Gates）

每个门禁列出**必须真实执行并通过**的检查。所有检查以最新一次运行结果为准；口头的「应该没问题」不算通过。

## G1 规格门禁（进入计划前）

- [ ] 规格文件存在于 `specs/NNN-*/spec.md`，包含：用户场景、编号功能需求 FR-x、编号验收标准 AC-x、非目标。
- [ ] 每条 AC-x 都是可客观验证的（有明确的检查方法，不含「好用」「合理」之类的模糊词）。
- [ ] 规格状态为「已确认」。

## G2 计划门禁（进入任务拆分前）

- [ ] `plan.md` 存在，方案覆盖所有 FR-x，且无 FR 之外的范围蔓延。
- [ ] 新增依赖（若有）已列明并说明必要性；与 `harness/context/domain.md` 技术栈一致。

## G3 任务门禁（进入实现前）

- [ ] `tasks.md` 存在，每个任务可独立验证，且所有 FR-x 被任务完整覆盖。

## G4 实现门禁（进入交付前）

前端（改动涉及 `web/` 时）：

```bash
pnpm -C web build && pnpm -C web lint
```

后端（改动涉及 `server/` 时）：

```bash
cd server && uv sync && uv run python -c "from app.main import app"
```

- [ ] 以上构建 / lint / 导入检查全部通过，0 错误 0 警告。
- [ ] `tasks.md` 中每个任务的验收方式已真实执行并通过。

## G5 交付门禁（宣布完成前）

- [ ] G4 全部通过（重跑一遍，以交付时的代码为准）。
- [ ] 端到端验证：`server/` 启动后 `GET /api/health` 返回 `{"ok": true}`；涉及 PDF 的改动必须真实调用 `POST /api/pdf` 并打开/检查生成的 PDF 内容。
- [ ] 规格回溯：`spec.md` 每条 AC-x 有对应的验证证据（命令输出、截图、响应内容）。
- [ ] 规格状态更新为「已实现」；受影响的 `harness/context/`、README 已同步。

## 门禁豁免

不允许豁免。唯一例外：纯文档改动（只动 `*.md`）可跳过 G4 的构建检查。
